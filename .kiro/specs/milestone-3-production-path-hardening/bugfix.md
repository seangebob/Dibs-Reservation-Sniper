# Bugfix Requirements Document

## Introduction

This bugfix hardens the production watch path after execution-based findings showed that the advertised watch lifetime, duplicate-delivery handling, live-demo provider state, and restart recovery are not reliable across real API and worker topologies. The must-fix core correctness scope is deadline-capable monitoring, cross-delivery single-flight processing, cancellation-safe state transitions, shared atomic mock booking state, startup reconciliation, provider-outage pacing, and test-first coverage of those paths. The lower-priority operability scope is unattended container execution, bounded Redis retention, bounded mock slot state, and accurate queue-mode health reporting. All scope in this document is required even when delivery is sequenced by priority.

## Bug Analysis

### Current Behavior (Defect)

1.1 WHEN a watch uses the default 200-attempt ceiling and the 180-second interval with 30-second jitter THEN the system can reach attempt exhaustion after roughly 10 hours and mark the watch `EXPIRED` before its calendar `expires_at`; this affects representative same-day, +1-day, +7-day, and +30-day watches whose remaining lifetime exceeds that polling horizon.
1.2 WHEN the attempt ceiling is capable of ending a watch before its reservation-date deadline THEN PromptRouter still tells the user that monitoring runs every few minutes until a slot opens or the date passes, without disclosing the earlier limit.
1.3 WHEN a very large attempt ceiling or an interval/jitter combination is configured THEN the system accepts an unbounded positive attempt value and has no lifetime-derived, overflow-safe policy contract that both caps work and prevents hot polling.
1.4 WHEN the same late-acknowledged Celery watch job is delivered two or more times for one cadence window THEN each delivery can poll and enqueue a successor, so two deliveries double the cadence and four deliveries quadruple it instead of preserving the configured anti-fingerprinting interval.
1.5 WHEN cancellation or a terminal transition races with an already-running or redelivered poll THEN stale work can save an older `ACTIVE` snapshot, double-count or lose attempt progress, enqueue another successor, or repeat booking and terminal notification side effects.
1.6 WHEN a worker dies while it owns a watch poll THEN there is no expiring ownership contract that prevents concurrent takeover while healthy yet permits bounded crash recovery without permanently wedging the watch.
1.7 WHEN the API and one or more Celery worker processes use `MockBookingAdapter` THEN generated slots, booked-slot state, and idempotency confirmations are process-local, so a worker-booked slot can still appear available through the API and replay works only in the process that created the booking.
1.8 WHEN mock availability searches and bookings execute concurrently or continue over time THEN search writes are not synchronized with booking reads and the generated-slot dictionary grows without a defined bound or eviction contract.
1.9 WHEN an `ACTIVE` watch exists in the active index but its queued job is lost before or during a restart THEN application startup performs no reconciliation, and the watch can remain `ACTIVE` forever even when it is due, overdue, or attempt-exhausted.
1.10 WHEN multiple API replicas start together, startup recovery fails partway, or the asyncio fallback is restarted THEN there is no recovery ownership, idempotent coordination, lease, or visible failure contract to prevent duplicate startup scheduling or explain unrecovered work.
1.11 WHEN the production watch paths are measured by tests THEN `monitor_watch.py` and `celery_app.py` are effectively uncovered and the Redis/Celery upgrade branch in `main.py` lacks coverage for retries, cleanup, queue selection, initial dispatch, recovery, redelivery, and shared mock state.
1.12 WHEN an operator needs to build and run the API and worker unattended THEN the repository has no `Dockerfile` or `.dockerignore` defining reproducible non-interactive API and worker execution.
1.13 WHEN Redis-backed watches become terminal or indexed documents disappear THEN terminal documents and all-watch index entries have no bounded retention, while stale IDs can remain in the all or active index indefinitely.
1.14 WHEN a caller requests `/health` THEN the response reports `watch_store` but not whether the selected watch queue is `celery` or `asyncio`, and it cannot distinguish selection from verified live readiness.
1.15 WHEN availability search or auto-booking raises `AdapterError` repeatedly THEN each outage result can consume the same user availability-attempt budget and retry at the normal cadence rather than applying outage-specific capped exponential backoff.

### Expected Behavior (Correct)

2.1 WHEN a watch is created with default settings for a same-day, +1-day, +7-day, or +30-day reservation date THEN the system SHALL allow an immediate first check and enough subsequent availability attempts to remain eligible through `expires_at` for every valid normal-jitter sequence; the required allowance SHALL be at least one greater than the ceiling of the remaining lifetime divided by the earliest valid normal delay, SHALL use checked bounded arithmetic, and SHALL let the calendar deadline rather than attempt exhaustion terminate those default cases. Provider-outage retries SHALL not reduce this allowance, every normal or outage delay SHALL remain jittered within its applicable bounds and capped at the remaining deadline, and no poll SHALL be scheduled after `expires_at`.
2.2 WHEN a configured safety ceiling intentionally cannot support monitoring through `expires_at` THEN the system SHALL retain that finite ceiling, disclose before or at watch creation that monitoring can stop after the stated maximum number of availability checks before the reservation date, and SHALL NOT claim unqualified monitoring until the date passes; WHEN the effective policy supports the full deadline THEN the existing deadline-based promise MAY be shown.
2.3 WHEN watch cadence, jitter, safety-ceiling, retention, lease, or backoff configuration is loaded THEN the system SHALL accept only finite values within documented positive bounds, reject combinations that can overflow supported persisted/configuration types or permit an unbounded hot-poll loop, and derive the effective attempt policy without wrapping, truncating, or allocating work proportional to an unchecked integer.
2.4 WHEN duplicate or redelivered jobs target the same watch cadence window in Celery or asyncio mode THEN the system SHALL grant at most one delivery an atomic single-flight claim for the provider poll and successor transition, produce at most one successor for that window, and keep the observable provider cadence within the one configured jittered schedule rather than multiplying it by delivery count; non-owners SHALL exit without polling or rescheduling.
2.5 WHEN cancellation, fulfillment, expiration, or another terminal transition races with claimed or stale work THEN the system SHALL use conditional/fenced state transitions so `CANCELLED`, `FOUND`, `BOOKED`, and `EXPIRED` cannot be overwritten by an older `ACTIVE` snapshot; one cadence window SHALL consume at most one availability attempt, an `AdapterError` window SHALL consume none, and a normal completed availability window SHALL commit exactly one attempt with its result. Booking SHALL remain idempotent for the watch key, each terminal event SHALL be externally observable at most once, and stale or duplicate deliveries SHALL return a terminal/no-op result without another booking, notification, or successor.
2.6 WHEN a poll owner crashes or its lease expires THEN another delivery or recovery sweep SHALL be able to take ownership after a finite configurable lease and complete the watch without a permanent wedge; no takeover SHALL occur while an unexpired owner remains valid, a former owner SHALL be unable to commit after losing ownership, and the default lease SHALL exceed the worker's 90-second hard task limit by a documented safety margin. A crash before a provider call SHALL not consume an attempt, while recovery of a window whose provider work may have started SHALL reuse the same cadence identity so its attempt can be committed no more than once.
2.7 WHEN Redis/Celery mode is selected for the live-demo mock provider THEN the system SHALL share durable mock slot, booking, booked-slot, and idempotency state across the API and all worker children through an injectable state boundary; concurrent booking of one slot with distinct keys SHALL produce exactly one confirmation and one unavailable result, replaying the same key from any process SHALL return the same confirmation, and every later search during the retention window SHALL exclude the booked slot. WHEN infrastructure is unavailable and in-memory mode is selected THEN the same atomic and idempotent behavior SHALL hold within that process without requiring Redis or Celery.
2.8 WHEN mock searches and bookings overlap or mock state reaches configured limits THEN the system SHALL synchronize slot publication with booking reads/writes and bound generated unbooked slot state by a configurable positive capacity and idle lifetime. Eviction SHALL prefer inactive unbooked slots and SHALL NOT remove a slot referenced by an in-flight operation, an unexpired confirmed booking, a booked-slot tombstone, or an idempotency record; confirmation, tombstone, and idempotency records SHALL default to at least seven days of replay protection and become eligible for coordinated cleanup only after that window, so eviction cannot make a protected booked slot appear available or break protected replay.
2.9 WHEN application startup finds watches in the selected store's active index THEN the system SHALL reconcile every available record: it SHALL atomically schedule each due watch whose `next_check_at` is at or before the current time at most once, schedule each future watch for its persisted due time rather than immediately, mark deadline-overdue or attempt-exhausted watches `EXPIRED` without polling, remove terminal or missing records from the active index, and never schedule a poll beyond `expires_at`.
2.10 WHEN multiple replicas or fallback instances run startup recovery THEN the system SHALL coordinate through a single finite leader lease or equivalent per-watch idempotent recovery claims so one eligible watch is startup-scheduled at most once across contenders and another instance can resume after owner failure. Redis/Celery mode SHALL coordinate across processes; asyncio mode SHALL reconcile all records available to its selected in-memory or Redis store while making no claim that process-local records survive process loss. Dispatch or reconciliation failures SHALL emit structured error details, expose degraded or unknown queue/recovery readiness without changing the existing top-level health meaning, release or expire ownership for bounded retry, and remain fully testable with injected clocks, queues, repositories, and locks.
2.11 WHEN behavior work for this bugfix begins THEN automated characterization or regression tests SHALL first cover task success, classified retry, retry exhaustion, cleanup, Celery configuration, Redis reachable and unreachable, Celery present and absent, queue selection, immediate first dispatch, startup recovery, lease expiry, duplicate deliveries, cancellation races, shared mock state, atomic booking, retention cleanup, health reporting, and outage backoff. These tests SHALL use fakes or doubles and single-run test commands without a live Redis server, broker, provider, or development server, SHALL exercise both Redis/Celery and in-memory/asyncio observable contracts, and SHALL coexist with all tests and requirements from `watch-route-worker-retry-hardening`.
2.12 WHEN an operator builds or starts the service from repository container assets THEN the system SHALL provide a `Dockerfile` and `.dockerignore` that build the API and worker reproducibly and run either role unattended with explicit non-interactive commands and an API health check. IF compose is extended with application services THEN the extension SHALL preserve the existing Redis and PostgreSQL services and their data/health behavior; the documented local flow SHALL retain Windows-friendly host commands and SHALL not require a watcher or interactive process.
2.13 WHEN a Redis-backed watch reaches a terminal state THEN the system SHALL remove it from the active index atomically, retain its document and all-watch listing for a configurable terminal TTL that defaults to seven days, and remove both the document and all-index membership after expiry. WHEN list, get, save, cleanup, or startup reconciliation encounters a missing, corrupt, terminal-in-active, or otherwise stale index member THEN the system SHALL prune that member without returning it as active; active documents SHALL remain durable until a terminal transition, and terminal records SHALL remain retrievable through the API for their full retention window.
2.14 WHEN `/health` is requested THEN the system SHALL preserve `status`, `service`, `config`, and `watch_store` semantics and add `watch_queue` with the actually selected value `celery` or `asyncio`; any separately reported queue or recovery readiness SHALL distinguish `ready`, `degraded`, and `unknown` based on checks actually performed and SHALL NOT report a broker as live merely because Celery imported or a mode was configured.
2.15 WHEN the n-th consecutive availability-search or auto-booking `AdapterError` occurs THEN the system SHALL record the outage without incrementing the user availability-attempt count and schedule a retry using the configured normal interval multiplied by `2^(n-1)`, bounded by a finite configurable maximum that defaults to 3,600 seconds, with configured jitter applied. The final provider-retry delay SHALL be no shorter than the anti-hot-poll floor and no later than `expires_at`; WHEN less than that floor remains before `expires_at` THEN the system SHALL schedule or perform deadline expiration without another provider call. A provider interaction that completes without `AdapterError`, including a valid empty availability result, SHALL reset the consecutive-outage count so the next normal miss uses the ordinary jittered cadence; reaching `expires_at` SHALL still produce the exact `EXPIRED` terminal outcome.

### Unchanged Behavior (Regression Prevention)

3.1 WHEN a valid watch is created THEN the system SHALL CONTINUE TO preserve existing watch API request and response contracts and dispatch the first background check immediately.
3.2 WHEN a user cancels an `ACTIVE` watch THEN the system SHALL CONTINUE TO transition it to `CANCELLED`, clear `next_check_at`, and prevent later provider polling or successor scheduling.
3.3 WHEN watch processing reaches an existing terminal condition THEN the system SHALL CONTINUE TO use the exact statuses `FOUND`, `BOOKED`, `EXPIRED`, and `CANCELLED` and the exact poll outcomes `NO_AVAILABILITY`, `FOUND`, `BOOKED`, `EXPIRED`, `ALREADY_FINISHED`, and `UNKNOWN_WATCH`; attempt-ceiling exhaustion SHALL CONTINUE TO map to `EXPIRED` rather than a new public terminal status.
3.4 WHEN a healthy provider returns no availability and no outage backoff is active THEN the system SHALL CONTINUE TO schedule one successor using the configured normal jitter intent, including the default 180-second interval with delays in the 150-to-210-second window.
3.5 WHEN a watch reaches its calendar deadline THEN the system SHALL CONTINUE TO derive `expires_at` as midnight after the reservation date in the configured reservation timezone, terminate it as `EXPIRED`, clear `next_check_at`, and avoid scheduling beyond that deadline.
3.6 WHEN Redis or Celery is absent or unreachable in an optional local setup THEN the system SHALL CONTINUE TO fall back to the supported in-memory and asyncio path without requiring external infrastructure, while accurately reporting the selected store and queue.
3.7 WHEN watch configuration is missing or invalid at request time THEN the system SHALL CONTINUE TO surface the retained `ConfigurationError` as HTTP 503 before date validation or watch creation rather than silently substituting defaults.
3.8 WHEN an auto-book watch attempts or replays a booking THEN the system SHALL CONTINUE TO use the stable idempotency key `watch:{watch_id}` and return the original confirmation for a protected replay.
3.9 WHEN the mock provider receives the same valid unbooked availability query THEN the system SHALL CONTINUE TO generate deterministic slot identities and availability, and SHALL CONTINUE TO identify all confirmations as mock behavior without presenting shared demo idempotency as a guarantee supplied by any real provider.
3.10 WHEN `/health` is requested in a healthy process THEN the system SHALL CONTINUE TO return HTTP success with top-level `status` equal to `ok`, service equal to `dibs-mvp`, the existing configuration state, and `watch_store` equal to the actually selected `redis` or `memory` store.
3.11 WHEN the worker encounters failures covered by `watch-route-worker-retry-hardening` THEN the system SHALL CONTINUE TO retry only explicitly recognized recoverable Redis or broker transport failures with the original exception and existing bounded worker retry policy, and SHALL CONTINUE TO propagate programming, validation, persisted-state, and other non-transient failures immediately.
3.12 WHEN worker resources are initialized and later shut down THEN the system SHALL CONTINUE TO serialize access to the persistent asynchronous runner and perform idempotent queue, Redis-client, and runner cleanup without constructing unused resources solely for cleanup.
3.13 WHEN existing automated tests run THEN the system SHALL CONTINUE TO run without live external services and preserve the current watch-route, worker-retry, API, booking, and mock-provider assertions.
3.14 WHEN local infrastructure is run with the existing compose file THEN the system SHALL CONTINUE TO preserve the Redis and PostgreSQL services, their health behavior, and the documented Windows-friendly local development flow.
3.15 WHEN a successful worker poll returns to Celery THEN the system SHALL CONTINUE TO return `watch_id`, the string-valued `outcome`, and `retry_in_seconds` with the existing meanings.
