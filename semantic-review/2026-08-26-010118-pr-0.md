# Fenced, recoverable watch-state design corrections

The revision tightens the production watch design around booking cancellation, schedule-marker ownership, far-future dispatch, bounded mock admission, legacy migration, cleanup, Lua validation, and Redis topology. The corrected marker, capacity, migration, outcome-mapping, and exact-Lua contracts address the first-pass gaps in those areas. Four correctness gaps still prevent cancellation safety and deadline-faithful execution for every accepted configuration. **Watch for:** **confirmed** ambiguous negative booking lookup can produce a false `CANCELLED`; **confirmed** the internal provider timeout has no outage transition; **confirmed** valid timeout settings can exceed the Celery soft-limit budget before commit; **confirmed** valid horizon/sweep settings can dispatch persisted future windows late; **confirmed** the Sentinel support claim exceeds the configured client topology.

**Verdict**: NEEDS_CHANGES

## High-level view

The booking permit gives cancellation a linearization point, but post-crash recovery treats `get_booking(...) == None` as proof that no external booking happened. The adapter contract only says no booking is currently known, so an ambiguous provider outcome can be committed as `CANCELLED`.

The full provider sequence has one timeout and the claim lease exceeds Celery's hard task limit. The timeout exit is not mapped into the provider-outage state machine, and the accepted 59-second provider timeout leaves at most one second under the fixed 60-second soft limit for the fenced commit.

Far-future Celery work remains durable until it enters a dispatch horizon. The accepted configuration permits the recovery sweep to be much longer than that horizon, so no coordinator is guaranteed to wake while a marker crosses into the horizon.

The Redis scripts are limited away from Cluster and tested as production Lua through an in-process Lua implementation. The Sentinel claim is not backed by Sentinel discovery or Celery Sentinel transport configuration; the existing single URL can address a primary directly but does not provide Sentinel-managed failover.

<summary>Issues (5)</summary>

1. **Ambiguous cancellation reconciliation** — **confirmed, blocking:** `get_booking(...) == None` does not prove an in-flight booking failed. Keep the watch pending on an unknown result and commit `CANCELLED` only after definitive absence or authoritative idempotent reconciliation.
2. **Provider timeout skips outage commit** — **confirmed, blocking:** the internal asyncio deadline raises `TimeoutError`, but only `AdapterError` enters no-attempt backoff. Translate that specific deadline into the fenced outage transition while preserving outer cancellation and Celery timeout behavior.
3. **No soft-limit commit margin** — **confirmed, blocking:** a valid 59-second provider timeout leaves at most one second before the 60-second Celery soft limit. Validate a shared inequality that reserves bounded repository and task-overhead time before soft/hard limits and lease expiry.
4. **Dispatch horizon shorter than recovery sweep** — **confirmed, blocking:** accepted settings can defer horizon entry for almost an hour. Require the horizon to cover coordinator sleep plus margin, or arm an exact wake-up for the next horizon crossing.
5. **Sentinel topology overclaim** — **confirmed, non-blocking:** direct `Redis.from_url` and a normal Celery broker URL do not implement Sentinel discovery/failover. Scope support to standalone/direct-primary Redis or add explicit Sentinel client, broker, readiness, and failover contracts.

<details><summary>Details</summary>

## Ambiguous booking recovery can turn an unknown side effect into `CANCELLED`

The recovery rule at `.kiro/specs/milestone-3-production-path-hardening/design.md:484` says that a missing `get_booking(watch:{watch_id})` result is enough to honor a pending cancellation. **Confirmed:** `ReservationAdapter.get_booking` returns a confirmation “when one is known”; `None` is not authoritative evidence that a timed-out or disconnected provider request did not complete. A provider can accept the idempotent booking while lookup remains unknown or stale, after which recovery commits `CANCELLED`, violating Requirements 2.5 and 3.2.

Recovery needs a tri-state result such as confirmed, definitely absent, or unknown. Unknown must retain a recoverable booking/cancellation phase and re-drive the same idempotency key or retry authoritative reconciliation; tests need this ambiguous case in addition to before-permit and after-permit ordering.

## Provider-sequence timeout bypasses outage accounting

The pseudocode wraps search, replay, and booking in `timeout(fullProviderSequenceTimeout)` but handles only a sequence ending with `AdapterError`. **Confirmed:** expiry of an asyncio timeout raises `TimeoutError`; without translation, the path escapes without an outage successor, leaves the marker deferred until lease recovery, and bypasses Requirement 2.15's no-attempt capped backoff.

Catch only the internal provider deadline and translate it to the fenced outage commit. A regression test must distinguish internal timeout, outer cancellation, and Celery termination, and assert that only `consecutive_outages` changes.

## Accepted provider timeout leaves no guaranteed fenced-commit budget

`WATCH_PROVIDER_CALL_TIMEOUT_SECONDS` accepts 59 seconds while Celery's soft limit remains 60 seconds, and the fenced commit occurs after the timed block. **Confirmed:** “finite Redis socket timeouts” defines neither a maximum nor an inequality tying provider work, repository commit, and task overhead to the soft limit. A provider response at its allowed deadline can repeatedly lose its commit despite the 120-second lease exceeding the 90-second hard kill.

Reject combinations unless `provider_sequence_timeout + maximum_commit_timeout + explicit_overhead_margin < task_soft_time_limit < task_hard_time_limit < claim_lease`. Exercise the boundary combinations rather than only defaults.

## Dispatch horizon can be shorter than the coordinator sleep

`WATCH_DISPATCH_HORIZON_SECONDS` accepts 30–3,600 seconds while `WATCH_RECOVERY_SWEEP_SECONDS` independently accepts 5–3,600 seconds. **Confirmed:** with a 30-second horizon and 3,600-second sweep, a marker can cross into the horizon immediately after a pass and receive no Celery publication until almost an hour later, violating Requirements 2.9 and 3.4.

Require the horizon to cover maximum coordinator sleep plus dispatch margin, or arm an exact wake-up for the next horizon crossing. Test the minimum-horizon/maximum-sweep combination against the persisted due time.

## Sentinel support is broader than the connection contract

The topology statement says the single Redis URL supports a Sentinel-managed primary. **Confirmed:** the repository uses `Redis.from_url`, and Celery receives the same normal broker URL; neither supplies Sentinel endpoints, a master name, discovery, or Sentinel broker transport options. A direct primary URL can execute the scripts but does not give the application Sentinel failover.

Scope the contract to standalone Redis or a directly addressed primary endpoint. Otherwise define redis-py and Celery Sentinel configuration, failover-aware readiness, and primary-change tests.
